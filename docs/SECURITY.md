# Security and privacy

Threat model: a single trusted Windows/browser account, private local data, optional authenticated cloud copy, and an explicitly trusted local MCP client. LifeOS does not defend against malware running as the same OS user, a compromised browser profile, administrator access, or an unlocked device. Prefer BitLocker/device encryption. SQLite and downloaded JSON backups contain plaintext personal content.

Supabase access requires an existing non-anonymous Auth user. Disable signups and anonymous sign-in in the project; create only the owner through the admin console. RLS compares auth.uid() to row ownership for SELECT/INSERT/UPDATE with explicit WITH CHECK. No service-role key, auth user_metadata authorization, SECURITY DEFINER functions, public records, or privileged API routes are used. The OTP template must display the token; the application never requests passwords or API secrets in chat.

Native auth credentials are held by the Windows credential mechanism through LifeOS-only entries (bounded 1600-byte chunks plus an atomically switched manifest, to accommodate Windows credential blob limits). Browser tokens and pending per-tab note drafts use session storage; web XSS could still read them. User content renders as text, never arbitrary HTML. Link schemas require HTTPS, reject embedded credentials, and restrict ChatGPT shortcuts to official ChatGPT hostnames. Native links pass a validating Rust command and open through the OS browser. Tauri capabilities expose no general shell, SQL, filesystem or credential-store interface. The native CSP prevents remote scripts and frames and allows only the configured Supabase network family.

The Next.js shell uses a pragmatic CSP allowing inline Next scripts/styles and eval (including development); nonce-based production CSP hardening remains a gate. It sets nosniff, no-referrer and DENY framing headers. No telemetry is implemented in LifeOS. Framework build telemetry can be disabled using `NEXT_TELEMETRY_DISABLED=1` and `TURBO_TELEMETRY_DISABLED=1`.

MCP uses stdio, not localhost HTTP. It requires both a launch environment opt-in and desktop setting; it only accesses the explicitly chosen existing database. There are twelve validated tools, no destructive delete tool, no arbitrary SQL, shell or unrestricted file tools. Successful actions are audited by tool name, record ID and timestamp; descriptions and credentials are not logged. The local OS account is the identity boundary. A client granted MCP access can read private LifeOS records by design. Disable the setting before sharing the device or granting an untrusted client.

No production cloud security audit or penetration test has been performed. Local PostgreSQL RLS tests exercise policies with distinct owners and anonymous claims, but do not prove a deployed Supabase project is configured correctly. See DELIVERY and SETUP for open gates.
